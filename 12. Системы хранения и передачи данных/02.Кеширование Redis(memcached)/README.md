## Задание 1. Кеширование

- Приведите примеры проблем, которые может решить кеширование.

*Приведите ответ в свободной форме*.

## Ответ:

1. ?**Чтение справочников и словарей (регионы, статусы, валюты)***
*Проблема*: приложение при каждом запросе делает lookup в БД за списком регионов/статусов/валютных курсов. При 1000+ RPS это тысячи мелких запросов, БД упирается в CPU/IO.
*Как решается*: кешировать справочники целиком или по ключам с TTL 5–30 минут.
*Пример*:Redis в Docker Compose; в ELK — хранить маппинги IP→город/регион в Redis и использовать в Logstash вместо частых запросов к БД.
2. ***Сессии и аутентификация***
*Проблема*: на каждый запрос приложение проверяет сессию/JWT в БД или внешнем auth-сервисе. Это узкое место при масштабировании.
*Как решается*: хранить активные сессии и валидные токены в Redis (или Memcached).
*Пример*: в контейнеризованной среде Redis как отдельный сервис; в микросервисах — централизованный session store.
3. ***Частые запросы к внешним API с лимитами***
*Проблема*: внешний сервис (геокодер, платёжный шлюз, курсы валют) имеет жёсткий RPS-лимит. При росте трафика лимит быстро исчерпывается.
*Как решается*: кешировать ответы внешних API с разумным TTL.
*Пример*: Nginx proxy_cache или Redis; в Terraform-скриптах можно кешировать результаты редких вызовов API (списки зон, квоты), чтобы не упираться в лимиты облачного API.
4. ***Nginx как HTTP‑кеш для API и статики***
*Проблема*: много повторяющихся GET-запросов на одни и те же ресурсы: списки товаров, регионы, JSON-справочники, CSS/JS.
*Как решается*: настроить proxy_cache в Nginx: отдельные зоны кеша, валидация через proxy_cache_use_stale, ключи по $request_uri.
*Пример*: Docker Compose с Nginx + бэкенд; в Yandex Cloud — Nginx перед группой ВМ.
5. ***Снижение нагрузки на БД при массовых чтениях***
*Проблема*: открытие каталога/дашборда вызывает десятки JOIN-запросов. При пиках БД деградирует.
*Как решается*: кешировать готовые DTO (карточки товаров, строки дашборда) по ключу product:123:view или dashboard:home:v2.
*Пример*: Redis sidecar в контейнерах; TTL под частоту обновления данных.
6. ***Агрегации и отчёты (суммы, средние, топ‑N)***
*Проблема*: каждый просмотр отчёта заново считает агрегации по большим таблицам. Это дорого по CPU и IO.
*Как решается*: сохранять результаты агрегаций в кеш с TTL или обновлять по событию.
*Пример*: Kibana - кешировать агрегаты по временным окнам; в приложении — кешировать топ‑10 товаров по продажам.
7. ***Отдача «устаревших, но хороших» данных при сбоях (stale‑while‑revalidate)***
*Проблема*: сервис временно недоступен (перезагрузка, деградация БД), а данные меняются редко.
*Как решается*: разрешить отдавать данные из кеша даже после истечения TTL на короткое время.
*Пример*: Nginx директивы proxy_cache_use_stale и proxy_cache_background_update; в Redis — паттерн stale-while-revalidate на уровне приложения.
8. ***Защита от повторяющихся запросов (дедупликация)***
*Проблема*: боты, автотесты, ошибочные циклы вызывают сотни одинаковых запросов.
*Как решается*: проверять наличие результата в кеше по уникальному ключу запроса.
*Пример*: Redis с ключом вида hash(request); в API Gateway или Nginx можно блокировать повторные запросы к дорогим эндпоинтам.
9. ***Оптимизация конфигурации и инфраструктурных данных***
*Проблема*: Terraform/скрипты при каждом запуске запрашивают списки зон, типов ВМ, IAM‑ролей, что увеличивает время выполнения и счёт за API‑запросы.
*Как решается*: кешировать инфраструктурные метаданные (списки ресурсов, квоты, статусы) с коротким TTL.
*Пример*: локальный JSON/YAML-кеш или Redis; для CI/CD — хранить результаты редких облачных API-запросов между запусками.
10. ***Ускорение обработки логов в ELK***
*Проблема*: Logstash делает lookup по IP/user/service на каждое событие, что замедляет пайплайн.
*Как решается*: держать маппинги в Redis и делать lookup там.
*Пример*: Logstash redis input/filter; в Docker Compose — Redis рядом с Logstash.
11. ***RabbitMQ: дедупликация сообщений и защита от шторма***
*Проблема*: в очередь попадает много одинаковых сообщений (дубли из разных источников) или резкий всплеск сообщений.
*Как решается*: перед публикацией проверять наличие «отпечатка» сообщения в Redis.
*Пример*: Producer проверяет SETNX по хешу payload; TTL равен времени актуальности сообщения.
12. ***CDN и edge‑кеширование***
*Проблема*: пользователи из разных регионов тянут одни и те же файлы (картинки, JS/CSS, JSON‑справочники), растёт трафик и latency.
*Как решается*: отдавать статику и редко меняющиеся JSON через CDN с кешированием на edge-узлах.
*Пример*: Yandex Cloud CDN или Cloudflare; TTL для статики — дни/недели, для справочников — минуты/часы.
13. ***Кеширование результатов тяжёлых вычислений***
*Проблема*: при каждом запросе пересчитываются сложные формулы, ML‑прогнозы, конверсии, рейтинги.
*Как решается*: сохранять результат по входным параметрам с TTL.
*Пример*: Redis/Memcached; ключ — хеш входных параметров.
12. ***Минимизация межсервисных вызовов в микросервисах***
*Проблема*: сервису A для ответа нужно вызвать сервисы B, C, D. При высокой нагрузке цепочка вызовов становится узким местом.
*Как решается*: кешировать ответы сервисов B/C/D локально или в общем Redis.
*Пример*: Sidecar‑кеш в контейнере или централизованный Redis; TTL подбирается под частоту изменения данных.
13. ***Оптимизация работы с файловой системой и локальными данными***
*Проблема*: частые обращения к файлам/каталогам (чтение конфигов, шаблонов, логов) вызывают IO‑нагрузку.
*Как решается*: кешировать содержимое файлов или метаданные каталогов в памяти.
*Пример*: в скриптах/приложениях — in‑memory кэш; в инфраструктуре — tmpfs для временных данных.
14. ***Снижение стоимости облачных ресурсов***
*Проблема*: рост числа запросов приводит к автоскейлингу контейнеров/ВМ и росту стоимости.
*Как решается*: кеш уменьшает число обращений к бэкенду → меньше реплик и очередей.
*Пример*: меньше подов в Kubernetes/контейнеров в Docker Compose, меньше очередей в RabbitMQ, меньше запросов к БД → экономия на CPU, RAM, IOPS.
15. ***Ускорение сборки и CI/CD***
*Проблема*: сборки/тесты долго скачивают зависимости и артефакты.
*Как решается*: локально кешировать зависимости (npm, pip, maven) и промежуточные слои образов.
*Пример*: Build cache в CI, Docker layer cache, локальный Nexus/Artifactory.
16. ***Оптимизация DNS и сетевых запросов***
*Проблема*: приложения делают много DNS‑запросов, что добавляет latency и нагрузку.
*Как решается*: использовать локальный DNS‑кеш (systemd‑resolved, dnsmasq) и кешировать записи в приложении.
*пример*: в контейнерах — настройка resolv.conf и локальный dnsmasq; в облаке — внутренние DNS с кешем.
17. ***Поддержка офлайн‑режима и слабой сети***
*Проблема*: клиент работает в условиях нестабильного соединения (дача, транспорт), данные должны быть доступны.
*Как решается*: клиентское кеширование (LocalStorage, IndexedDB, SQLite) для справочников, форм, истории.
*Пример*: веб‑приложение с Service Worker; мобильное приложение с локальной БД.

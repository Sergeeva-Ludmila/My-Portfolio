## Ответ:

**Для выполнения этого задания были использованы:**

**1. Suricata** (для защищаемой системы) - это мощный инструмент для сетевой безопасности с открытым исходным кодом. Я бы описала его так: это движок, который в реальном времени анализирует сетевой трафик, ищет в нём признаки угроз и может не только сообщать об этом, но и активно блокировать подозрительные действия. Его разрабатывает Фонд открытой информационной безопасности (OISF).

**2. Fail2Ban** (для защищаемой системы) - то инструмент для автоматической защиты серверов (чаще всего на Linux и Unix-подобных системах) от несанкционированного доступа, в частности от брутфорс-атак (перебора паролей). Название — игра слов: fail (неудача, сбой) + ban (блокировка, запрет).

**3. Kali Linux** (система злоумышленника) - это специализированный дистрибутив операционной системы Linux с открытым исходным кодом, созданный командой Offensive Security для задач в сфере информационной безопасности. Его основная цель — проведение расширенного тестирования на проникновение (пентеста), анализ уязвимостей систем, цифровая криминалистика и реверс-инжиниринг.

**4. Ubuntu 24.04** (защищаемая система) - это дистрибутив операционной системы Linux с открытым исходным кодом, выпущенный компанией Canonical в апреле 2024 года. У этой версии есть кодовое имя — Noble Numbat (в переводе с английского —  «благородный намбат»).

**5. Nmap (Network Mapper)** — это бесплатная утилита с открытым исходным кодом, созданная для исследования сетей, аудита их безопасности и анализа сетевых устройств. Она позволяет обнаруживать активные хосты, определять открытые порты и сервисы на них, выявлять операционные системы, а также анализировать настройки сетевых экранов и других защитных механизмов.

**6. Hydra (или THC Hydra)** — программа для параллельного подбора паролей, встроенная в различные операционные системы для пентеста, такие как Kali Linux, Parrot OS и другие.

**18 - Настройка Fail2Ban: белый список и jail для sshd**
1. Определение IP-адреса текущей SSH-сессии:
```bash
- echo $SSH_CLIENT
```
**Описание команды:** переменная окружения SSH_CLIENT содержит IP-адрес, с которого установлено текущее SSH-подключение (первое поле вывода), а также порт клиента и порт сервера. Знание этого адреса необходимо перед настройкой ignoreip: если в белом списке не указать адрес машины администратора, при отработке брутфорса можно случайно заблокировать и свою собственную сессию.

2. Создание файла jail.local с настройками sshd и белым списком:
```bash
- sudo tee /etc/fail2ban/jail.local > /dev/null <<EOF
[sshd]
enabled  = true
port     = 22
backend  = systemd
maxretry = 3
findtime = 10m
bantime  = 10m
ignoreip = 127.0.0.1/8 ::1 192.168.56.1
EOF
```
**Описание команды:**команда создаёт (или перезаписывает) файл /etc/fail2ban/jail.local — локальную конфигурацию Fail2Ban. Именно jail.local, а не правка jail.conf, является рекомендуемым способом: при обновлении пакета jail.conf перезаписывается, а пользовательский .local сохраняется. Конструкция sudo tee > /dev/null <<EOF используется потому, что перенаправление sudo > файл не срабатывает (права теряются на уровне shell), а tee записывает текст от имени root.

**27 - Запуск SYN‑сканирования - sS** (запускаем на атакующей машине Kali Linux)
```bash
- sudo nmap -sS 192.168.56.117
```

![alt text](<Screenshots/Задание 1-19.png>)

![alt text](<Screenshots/Задание 1-20.png>)

**Результат:** сработали 4 сигнатуры «Suspicious inbound» (SID 2010935, 2010936, 2010937, 2010939 — порты 1433, 1521, 3306, 5432) и «Potential VNC Scan 5800–5820» (SID 2002910). Классификация — Potentially Bad Traffic, Priority 2.

**Вывод:** Suricata детектирует полусинхронное сканирование по факту отправки SYN-пакетов на защищаемые порты. Алерты выдаются на закрытые порты, на которых сервисов нет — IDS реагирует на сам акт зондирования, а не на доступность сервиса. Источник использовал небольшое число исходных портов (48230, 48232) с повторными отправками — типичный почерк -sS, когда Nmap не завершает handshake и переиспользует сокеты. Порог limit, count 5, seconds 60, track by_src ограничил выдачу 1–2 алертами на порт, не допуская лавины однотипных событий.

**28 - Запуск TCP Connect‑сканирования - sT** (запускаем на атакующей машине Kali Linux)
```bash
- sudo nmap -sT 192.168.56.117
```

![alt text](<Screenshots/Задание 1-21.png>)

![alt text](<Screenshots/Задание 1-22.png>)

**Результат:** сработал тот же набор из 5 сигнатур, состав алертов идентичен -sS.

**Вывод:** правила реагируют на первый пакет соединения (SYN), поэтому полный handshake не спасает скан от детекции — сигнатуры не различают, завершится ли соединение. Характерная деталь: в отличие от -sS, каждый коннект шёл с нового исходного порта (35086, 35094, 52728, 52738, 54074, 54078 и др.) — это следствие того, что ядро ОС выделяет отдельный ephemeral-порт на каждое полноценное TCP-соединение.Cигнатурный детект на SYN-флаг не различает stealth- и connect-сканы — алерты идентичны, различия видны только при анализе паттерна трафика.

**29 - Запуск ACK‑сканирования - sA** (запускаем на атакующей машине Kali Linux)

```bash
- sudo nmap -sA 192.168.56.117
```

![alt text](<Screenshots/Задание 1-23.png>)

**Результат:** наблюдаем - алертов нет, лог пустой.

**Вывод:** это ожидаемое и важное наблюдение. Все применимые сигнатуры содержат условие flags:S и срабатывают только на пакеты с флагом SYN; ACK-скан шлёт пакеты только с флагом ACK, поэтому ни одна сигнатура не сработала. Это демонстрирует принципиальное ограничение сигнатурного подхода: IDS обнаруживает ровно те активности, которые описаны в наборах правил, и не выявляет атаки «по поведению». Тихие сканы без SYN остаются невидимыми для дефолтного набора ET Open — для их детекции требуются дополнительные правила (например, на flags:A с порогом по частоте) или методы обнаружения аномалий.

В рамках двух экспериментов оценивалась эффективность защиты SSH‑сервиса при разных подходах к подбору учётных данных:
- **Вариант - 1** (логин и пароль добавлены в словари для перебора). При отсутствии дополнительной защиты такой подбор потенциально способен выявить слабые учётные данные. В реальной среде это привело бы к росту числа неудачных попыток входа, которые фиксируются в журналах аутентификации и могут быть использованы системами мониторинга.
- **Вариант - 2** (защита активна — Fail2Ban + правила iptables). Даже при наличии «угадываемых» учётных данных механизм Fail2Ban своевременно ограничивает доступ: после заданного числа неудачных попыток IP‑адрес блокируется на уровне фаервола (через цепочку f2b-sshd в iptables). Это не даёт злоумышленнику продолжить перебор и фактически нейтрализует угрозу, связанную с простыми паролями.
- **Итог:** наличие активной защиты (Fail2Ban в связке с фаерволом) существенно повышает устойчивость SSH‑сервиса к атакам перебора, даже если учётные данные потенциально уязвимы. Защита работает как «страховка» от слабых паролей, ограничивая количество попыток и изолируя подозрительные IP‑адреса.

## Ответ:

**Цель работы:**
Научиться шифровать пользовательские данные средствами eCryptfs (встроенной криптографической файловой системы ядра Linux): установить утилиты, создать тестового пользователя, зашифровать его домашний каталог и проверить, что данные хранятся на диске в зашифрованном виде, но остаются доступны владельцу.

**eCryptfs** — это криптографическая файловая система для Linux. Я бы описала её так: она работает «поверх» обычной файловой системы и прозрачно шифрует, а при необходимости дешифрует содержимое файлов и папок. При этом все нужные для этого криптографические метаданные хранятся прямо внутри зашифрованных файлов. Это ключевое отличие от многих других решений: благодаря этому зашифрованные файлы можно спокойно копировать, перемещать, делать с ними резервные копии — и они останутся корректно расшифрованными на другом устройстве.

## Задание 2

1. Установите поддержку **LUKS.**
2. Создайте небольшой раздел, например, 100 Мб.
3. Зашифруйте созданный раздел с помощью **LUKS.**

*В качестве ответа пришлите снимки экрана с поэтапным выполнением задания.*

## Ответ:

**Цель работы:**
Отработать механизм шифрования блочных устройств с помощью LUKS (Linux Unified Key Setup) на примере loop-устройства. Научиться создавать зашифрованный контейнер, монтировать его, записывать данные, а также демонстрировать невозможность доступа к данным без ключа

**LUKS** - (от Linux Unified Key Setup) — это стандарт (спецификация) для шифрования дисков в операционных системах на базе ядра Linux. Его главная задача — обеспечить безопасный и удобный способ управления ключами расшифровки, чтобы защитить данные на физических или виртуальных носителях от несанкционированного доступа.

**1 - Установка поддержки LUKS**
Установка криптографического пакета - утилитy cryptsetup, которая отвечает за работу со стандартом шифрования LUKS в Linux и проверяем установку.
```bash
- sudo apt update
- sudo apt install -y cryptsetup
- cryptsetup --version
```

![alt text](<Screenshots/Задание 2-1.png>)

**2 - создание образа и привязка к loop‑устройству**
Генерируем пустой файл-образ размером 100 МБ, полностью забитый нулями, и связываем его со свободным виртуальным loop-слотом системы:
```bash
- dd if=/dev/zero of=/home/mila/luks_disk.img bs=1M count=100
- ls -lh /home/mila/luks_disk.img
- sudo losetup -f
- sudo losetup -fP /home/mila/luks_disk.img
- sudo losetup -a
```

![alt text](<Screenshots/Задание 2-2.png>)

![alt text](<Screenshots/Задание 2-3.png>)

![alt text](<Screenshots/Задание 2-4.png>)

**Результат:**
- подготовили «диск» для шифрования: создали файл‑образ на 100 МБ и превратили его в блочное устройство через loop.
- система видит его как /dev/loop21, и теперь с ним можно работать точно так же, как с реальным разделом — форматировать, шифровать, монтировать.

**3 - Инициализируем LUKS‑заголовок (шифруем диск)**
```bash
- sudo cryptsetup luksFormat /dev/loop21
- sudo cryptsetup luksDump /dev/loop21
```

![alt text](<Screenshots/Задание 2-5.png>)

![alt text](<Screenshots/Задание 2-6.png>)

**Результат:**
- в ходе выполнения этапа на loop-устройстве /dev/loop21 был инициализирован LUKS-заголовок командой cryptsetup luksFormat. Перед перезаписью данных утилита запросила подтверждение (YES в заглавных буквах) и предложила установить пароль доступа, вводимый дважды. Пароль в отчёт не включён и хранится отдельно.
- команда cryptsetup luksDump /dev/loop21 подтвердила корректное создание контейнера: в заголовке отображены версия LUKS 2, используемый алгоритм шифрования (aes-xts-plain64), параметры хеширования, UUID тома и активные слоты ключей (по умолчанию занят слот 0).
- таким образом, блочное устройство переведено в формат LUKS-контейнера. Данные на нём с этого момента хранятся в зашифрованном виде и недоступны без ключа шифрования, что будет продемонстрировано на последующих этапах работы.

**4 - Открываем LUKS‑контейнер и создаём файловую систему**
```bash
- sudo cryptsetup luksOpen /dev/loop21 encrypted_disk
- sudo mkfs.ext4 /dev/mapper/encrypted_disk
```

![alt text](<Screenshots/Задание 2-7.png>)

**Результат:**
- зашифрованный LUKS‑контейнер на устройстве /dev/loop21 был открыт командой cryptsetup luksOpen с присвоением имени маппинга encrypted_disk.
- ввод пароля (не включён в отчёт) подтвердил возможность аутентификации и разблокировки устройства.
- на логическом устройстве /dev/mapper/encrypted_disk была создана файловая система ext4 с помощью утилиты mkfs.ext4.
- в процессе форматирования инициализированы суперблок, группы блоков, таблица inode и журнал файловой системы   - это делает устройство пригодным для хранения данных.
- Таким образом, подготовлен полностью рабочий зашифрованный том: он доступен системе как блочное устройство, имеет корректную файловую систему и готов к записи пользовательских данных.

**5 - Монтируем диск и пишем тестовые данные и проверяем статус**
```bash
- sudo mkdir -p /mnt/encrypted_security
- sudo mount /dev/mapper/encrypted_disk /mnt/encrypted_security
- echo "Mine hemmelige og konfidensielle data i LUKS 2026" | sudo tee /mnt/encrypted_security/test.txt
- ls -la /mnt/encrypted_security
- cat /mnt/encrypted_security/test.txt
- df -h /mnt/encrypted_security
```

![alt text](<Screenshots/Задание 2-8.png>)

**Результат:**
- примонтировали наш LUKS‑диск в понятную папку /mnt/encrypted_security и положили туда тестовые данные.
- файл test.txt создался, его видно через ls, содержимое читается через cat — значит, шифрование не мешает работать с данными, когда контейнер открыт.
- df -h показал, что из 100 МБ образа реально доступно около 75 МБ — это нормально: часть места ушла на заголовок LUKS и служебные структуры ext4 (журнал, inode и т. п.). Занято всего несколько килобайт — всё как и должно быть для «свежего» диска.
- данные пишутся и читаются, система видит его как обычный диск — только с гарантией, что без пароля никто эти данные не увидит.

**6 - Демонстрация защиты**
```bash
- sudo umount /mnt/encrypted_security
- sudo cryptsetup luksClose encrypted_disk
- file /home/mila/luks_disk.img
- strings /home/mila/luks_disk.img | grep -i secret
```

![alt text](<Screenshots/Задание 2-9.png>)

**Рузультат:**
- выполнили корректное отключение зашифрованного тома: сначала размонтировали точку /mnt/encrypted_security,
- затем закрыли LUKS‑контейнер через luksClose. Это стандартная процедура безопасного вывода устройства из эксплуатации — без неё нельзя освобождать loop‑устройство.
- проверка через file подтвердила, что файл‑образ остаётся валидным LUKS2‑контейнером: система корректно распознаёт заголовок, но не имеет доступа к содержимому.
- ключевой тест безопасности — попытка извлечь осмысленные данные через strings | grep -i secret — дал пустой результат. Это ожидаемое поведение: без ввода пароля LUKS не позволяет прочитать ни содержимое, ни маркеры данных. Даже поиск общеупотребимых слов не помогает — контейнер выглядит как набор случайных байтов.
- механизм защиты подтверждён - доступ к данным контролируется паролем, а отсутствие «читаемого текста» в образе — прямое доказательство, что шифрование реально работает на уровне блочного устройства.

**7 - Повторное открытие: доказываем, что данные не пропали**
```bash
- sudo cryptsetup luksOpen /dev/loop21 encrypted_disk
- sudo mount /dev/mapper/encrypted_disk /mnt/encrypted_security
- cat /mnt/encrypted_security/test.txt
```

![alt text](<Screenshots/Задание 2-10.png>)

**Результат:**
- выполнили повторное открытие LUKS‑контейнера с вводом пароля и примонтировали том в /mnt/encrypted_security. - проверка через cat подтвердила сохранность файла test.txt и его содержимого.
- данные не потеряны — шифрование скрывает их при закрытом контейнере, но не повреждает при корректной работе с томом. Это доказывает целостность механизма LUKS: защита работает без потери пользовательских данных.

**8 - Финальная очистка**
```bash
- sudo umount /mnt/encrypted_security
- sudo cryptsetup luksClose encrypted_disk
- sudo losetup -d /dev/loop21
```

![alt text](<Screenshots/Задание 2-11.png>)

**Результат:**
- выполнили корректную очистку окружения: размонтировали точку /mnt/encrypted_security,
- закрыли LUKS‑контейнер и освободили loop‑устройство через losetup -d.
- все ресурсы возвращены системе, зашифрованный том больше не доступен, loop‑интерфейс свободен. Это обязательный финальный этап — он исключает утечки доступа и гарантирует чистое состояние среды после работы.

**AppArmor** (от англ. Application Armor) — это механизм безопасности для операционных систем на базе Linux. Его задача — ограничивать возможности приложений, чтобы снизить риски в случае их уязвимости или компрометации. Проще говоря, он работает по принципу «белого списка»: разрешает только явно указанные действия, а всё остальное блокирует.

- результатом стало подтверждение, что на используемом ядре директивы deny network inet не обеспечивают блокировку ICMP‑сокетов. Реальная защита достигается за счёт комбинации механизмов: сужения ping_group_range для запрета SOCK_DGRAM и запрета capability net_raw для блокировки SOCK_RAW. Наглядность отказов подтверждена через strace (ошибки EACCES, EPERM) и тестовую программу, выводящую понятные сообщения об ошибках.
- контроль легитимной утилиты ping подтвердил, что защита корректно привязана к пути исполнения. По завершении эксперимента стенд был полностью возвращён в исходное состояние: AppArmor удалён, временные файлы очищены, оригинальный man восстановлен.

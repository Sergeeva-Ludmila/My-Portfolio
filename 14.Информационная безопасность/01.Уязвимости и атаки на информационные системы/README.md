-  Порт 25/TCP как стандартный порт протокола SMTP, предназначенный для передачи почты между серверами. Его состояние служит индикатором наличия почтового сервиса на периметре: открытый порт формирует вектор атак (в т. ч. SMTP‑enumeration), закрытый — подтверждает отсутствие сервиса в зоне прямого доступа. Проверка позволяет либо обосновать необходимость защиты активного SMTP, либо зафиксировать отсутствие соответствующего риска при отсутствии использования сервиса.
- Порт 5555/TCP — заведомо неактивный порт. Нужен для демонстрации чёткого статуса closed: сервер отвечает RST, подтверждая, что никто не слушает порт. Это для понимания, как TCP‑сканирование уверенно фиксирует отсутствие сервиса.
- Порт 111/UDP (rpcbind) — реально работающий UDP‑сервис. Позволяет показать, что в UDP тоже бывает однозначный статус open, если служба активно отвечает на запросы.
- Порт 5555/UDP — тот же номер, но по UDP. Выбран специально, чтобы раскрыть специфику UDP‑сканирования: из‑за отсутствия ответа статус часто бывает open|filtered, и это наглядно иллюстрирует, почему в UDP нельзя так же надёжно, как в TCP, определить состояние порта.

- Пакеты 6, 9, 10: сервер → сканер ICMP Destination unreachable (Port unreachable) — ядро явно сообщило, что порт 5555 закрыт → Nmap ставит closed;
- Пакеты 4–5 и 7–8: обмен по порту 111 — Portmap V104316 proc-0 Call (Reply In 7) и RPC Continuation, затем Portmap proc-0 Reply (Call In 4). Служба rpcbind реально ответила на запрос данными → порт 111/UDP — open;
Пустых ответов «в тишину» не зафиксировано: для обоих проверяемых портов есть однозначная реакция.
**Итог:** Nmap совпадает с трафиком: 111/UDP — open (rpcbind), 5555/UDP — closed (ICMP Port unreachable). Захват подтверждает особенность UDP‑сканирования: статус порта определяется не флагами, а наличием ответа службы или ICMP‑сообщения — и в данном случае оба статуса получены.

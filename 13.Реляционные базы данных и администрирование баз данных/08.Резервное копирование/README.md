## Задание 1. Резервное копирование

**Кейс**

*Финансовая компания решила увеличить надёжность работы баз данных и их резервного копирования.*

Необходимо описать, какие варианты резервного копирования подходят в случаях:

1.1. Необходимо восстанавливать данные в полном объёме за предыдущий день.

1.2. Необходимо восстанавливать данные за час до предполагаемой поломки.

1.3.* Возможен ли кейс, когда при поломке базы происходило моментальное переключение на работающую или починенную базу данных.

*Приведите ответ в свободной форме.*

## Ответ:

**1.1.Необходимо восстанавливать данные в полном объёме за предыдущий день.**
1. Выбираем: полное резервное копирование (Full backup) раз в сутки.
2. Почему: цель — вернуть базу целиком на вчерашнее состояние. Полная копия содержит все данные целиком, для восстановления не нужно ничего докатывать — взяли копию и развернули.
3. Плюсы:
- самое простое и предсказуемое восстановление — один файл, одна операция;
- не зависит от цепочки других копий, если одна копия битая — берём предыдущую;
- легко проверять и тестировать восстановление.
4. Минусы:
- большой объём хранилища: каждая копия — это вся база целиком;
- долгое создание копии и нагрузка на систему в момент бэкапа;
- глубина восстановления ограничена частотой копий: daily-бэкап не вернёт состояние «на час до полудня.

**1.2.Необходимо восстанавливать данные за час до предполагаемой поломки.**
1. Выбираем: связку — полный бэкап раз в сутки + инкрементальные (или дифференциальные) копии каждый час.
2. Почему: одного полного бэкапа в день мало — потеряем до 23 часов данных. Часовые копии сокращают окно потери данных до ~1 часа. Восстановление идёт так: последний полный бэкап → наложение часовых копий до нужного момента.
3. Плюсы:
- минимальное окно потери данных — около часа;
- экономия места по сравнению с часовыми полными копиями;
- инкрементальные копии делаются быстро и почти не грузят систему.
4. Минусы:
- сложнее в сопровождении: нужно строго соблюдать порядок цепочки копий;
- дифференциальные копии к концу дня растут в размере;
- инкрементальная цепочка уязвима: одна битая копия рушит всё, что после неё;
- окно в час всё равно есть — если данные терять нельзя вообще, нужны транзакционные журналы (WAL/binlog), позволяющие откатиться на любую секунду.

**1.3*.Возможен ли кейс, когда при поломке базы происходило моментальное переключение на работающую или починенную базу данных.**
1. Выбираем: кластер с репликацией и автоматическим failover.
2. Почему: обычные бэкапы тут не спасут — восстановление из архива занимает часы, а нужно переключение за секунды. Поэтому строим вторую работающую копию базы (реплику), которая постоянно синхронизируется с основной. При аварии ПО кластера (например, Patroni для PostgreSQL, AlwaysOn для MS SQL, MySQL InnoDB Cluster) само обнаруживает сбой и назначает реплику новой основной базой. Переключение занимает секунды–минуты, пользователи могут почти не заметить простоя.
3. Плюсы:
- практически нулевое время простоя — не нужно ждать восстановления из бэкапа;
- реплика — «горячий» резерв, она живая и постоянно обновляется;
бонус: реплики можно нагружать чтением, разгружая основную базу.
4. Минусы:
- это уже не «бэкап», а отдельная инфраструктура: дороже в железе и сопровождении;
- репликация ≠ резервное копирование: если случайно удалили таблицу, она удалится и на репликах — бэкапы всё равно нужны;
- синхронная репликация гарантирует отсутствие потери данных, но замедляет запись;
- асинхронная — быстрее, но при сбое можно потерять последние транзакции;
- нужно тщательно протестировать автоматический failover — «split brain» (обе базы считают себя основной) — известная проблема плохо настроенных кластеров.

## Задание 2. PostgreSQL

2.1. С помощью официальной документации приведите пример команды резервирования данных и восстановления БД (pgdump/pgrestore).

2.1.* Возможно ли автоматизировать этот процесс? Если да, то как?

*Приведите ответ в свободной форме.*

## Ответ:

**2.1.С помощью официальной документации приведите пример команды резервирования данных и восстановления БД (pgdump/pgrestore).**

**1 - Резервное копирование** — **pg_dump** выгружает логическую копию базы: схему (таблицы, индексы, функции) и данные в виде набора команд **SQL** или в бинарном формате. Пример из официальной документации **PostgreSQL**:
```bash
- pg_dump mydb > db.sql
```
*Что делает:* выгружает базу **mydb в файл db.sql** — это обычный **SQL**-скрипт со всеми командами создания объектов и вставки данных. Его можно читать глазами и применять на любой версии **PostgreSQL**.
*Восстановление* из такого скрипта выполняется утилитой **psql** — она построчно выполняет SQL-команды из файла:
```bash
- psql -X -d newdb -f db.sql
```
*Что делает:* восстанавливает данные из **db.sql в базу newdb**. Флаг **-X** отключает автозагрузку файла **.psqlrc, -f** указывает файл со скриптом. Важный нюанс: целевую базу нужно создать заранее пустой, документация рекомендует **createdb -T template0 newdb** — чтобы в ней не было лишних объектов из шаблона **template1**.
**2 - бинарный формат + pg_restore**
```bash
- pg_dump --format=custom mydb > mydb.dump
- pg_restore --dbname=mydb mydb.dump
```
*Что делает:* первый шаг сохраняет дамп в сжатом **custom-формате** — это не SQL-текст, а архив, из которого можно выбирать отдельные таблицы и объекты. Второй шаг — **pg_restore** — читает этот архив и восстанавливает объекты в базу **mydb**.
У **pg_restore** есть полезные опции:
**-c (--clean)** — удалить старые объекты перед восстановлением,
**-C (--create)** — создать базу,
**-j N** — параллельное восстановление в N потоков (заметно ускоряет на больших базах).
*Ограничение pg_dump*: он копирует только одну базу и не сохраняет роли и табличные пространства. Если нужен весь кластер целиком — используется **pg_dumpall**.


**2.1*.Возможно ли автоматизировать этот процесс? Если да, то как?**
Да, возможна. Стандартная схема — скрипт-обёртка + планировщик cron.
1. Скрипт бэкапа:
```bash
#!/bin/bash
BACKUP_DIR=/var/backups/postgresql
pg_dump --format=custom --file=$BACKUP_DIR/mydb_$(date +%F).dump mydb
find $BACKUP_DIR -name "*.dump" -mtime +30 -delete
```
Cкрипт делает дамп базы mydb в бинарном формате с именем файла по дате (например, mydb_2026-11-05.dump), а затем строкой find ... -mtime +30 -delete удаляет копии старше 30 дней — это ретеншен, чтобы хранилище не переполнялось.
2. Планировщик cron — запускает скрипт по расписанию, например каждую ночь в 2:00, когда нагрузка на базу минимальна:
```cron
0 2 * * * /usr/local/bin/backup.sh >> /var/log/pg_backup.log 2>&1
```
Пять полей задают время (минуты, часы, день месяца, месяц, день недели), дальше — команда. Логи выполнения дописываются в файл, чтобы потом можно было проверить, прошёл ли бэкап.

## Задание 3. MySQL

3.1. С помощью официальной документации приведите пример команды инкрементного резервного копирования базы данных MySQL.

3.1.* В каких случаях использование реплики будет давать преимущество по сравнению с обычным резервным копированием?

*Приведите ответ в свободной форме.*

## Ответ:

**3.1.С помощью официальной документации приведите пример команды инкрементного резервного копирования базы данных MySQL.**
В **MySQL** инкрементные копии строятся на бинарном журнале **(binlog):** сервер, запущенный с опцией **--log-bin**, записывает в него все изменения данных. Согласно документации, бинарные журналы и образуют набор инкрементных копий.
**1. Полная копия с ротацией журналов** — пример из документации:
```bash
- mysqldump --single-transaction --flush-logs --master-data=2 --all-databases > full_backup.sql
```
*Что делает:* **--single-transaction** снимает дамп без блокировки таблиц; **--flush-logs** закрывает текущий **binlog** и начинает новый — так все изменения после полного бэкапа попадут в новые файлы журнала; **--master-data=2** записывает в дамп имя и позицию нового **binlog** — это стартовая точка для восстановления.
**2. Инкрементная копия** — после **FLUSH LOGS** скопировать накопленные бинарные журналы:
```bash
- mysql -e "FLUSH LOGS;"
- cp /var/log/mysql/mysql-bin.000007 /var/log/mysql/mysql-bin.000008 /var/backups/mysql/
```
*Что делает*: команда **FLUSH LOGS** вращает журнал, и все **binlog-файлы** с момента последней копии (в примере — 000007 и 000008) можно забрать в хранилище — это и есть инкрементный бэкап.
**Восстановление:** сначала накатывается полный дамп, затем бинарные журналы через **mysqlbinlog:**
```bash
-  < full_backup.sql
- mysqlbinlog mysql-bin.000007 mysql-bin.000008 | mysql
```
**Альтернатива для Enterprise-редакции — MySQL Enterprise Backup с опцией --incremental:**
```bash
- mysqlbackup --incremental --incremental-base=history:last_backup \
  --backup-dir=/home/dbadmin/temp_dir \
  --backup-image=incremental_image1.bi backup-to-image
```
*Что делает:* **--incremental** копирует только изменённые с прошлого бэкапа страницы **InnoDB**, **--incremental-base=history:last_backup** берёт за основу последнюю копию из истории — никакие LSN вручную указывать не нужно.

**3.1*.В каких случаях использование реплики будет давать преимущество по сравнению с обычным резервным копированием?**
1. Минимальный простой (RTO близко к нулю). Восстановление из дампа большой базы занимает часы, а переключение на реплику при поломке мастера — секунды–минуты.
2. Непрерывность и актуальность данных (RTO/RPO в секундах). Реплика постоянно синхронизируется с мастером, тогда как даже часовые инкременты оставляют окно потери данных.
3. Разгрузка мастера. Тяжёлые аналитические запросы и отчёты можно отправлять на реплику, не замедляя основную базу. Бэкап такой возможности не даёт — наоборот, mysqldump сам создаёт нагрузку.
4. Снятие копий без нагрузки на продакшен. Полный бэкап можно делать с реплики — основной сервер при этом не тормозит.
5. Защита от отказа самого сервера. Если упало железо мастера, реплика уже живая и готовая — ждать восстановления из архива не нужно.
